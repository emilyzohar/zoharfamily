# Zohar Family — private website admin

This version turns `admin.html` into a simple private content manager for the existing Dropbox-powered family website.

## What changed in this version

- The first screen contains **only the password form**. The editor is not shown until the password is accepted by the Cloudflare Worker.
- “What are you adding?” is now a set of large tabs: **Recipe, Trip, Memories, Merch, Person's Page**.
- Every section has a **Preview** button. The preview is generated locally in the browser before anything is uploaded to Dropbox.
- Travel coordinates are still automatic, but the map can now be **zoomed to 350%** and scrolled for precise placement.
- Travel “Generation” is now presented to users as an open-text **Filter Name** field. A revised `travel.js` is included so arbitrary human-readable filter names work safely.
- Recipes no longer ask for a folder name or display order. New recipe `.txt` files are stored directly in the Recipes folder, matching the existing recursive recipe loader.
- Recipe images are put automatically in `Recipes/images/` and referenced from the recipe text file.
- Memories can contain **photos/videos, web links, or both**.
- Merch no longer asks for a folder name or display order. The folder is created from the item name and the next display order is calculated automatically from existing merch metadata.
- A Person's Page now clearly supports:
  - Works
  - personal Recipes
  - personal Travel
  - personal Memories
  - a customizable personal **Collection** that uses the existing Merch card/quick-view design.

## Files to put on the website

Copy these beside the existing `index.html`:

- `admin.html`
- `admin.css`
- `admin.js`

Also replace the site's current `travel.js` with the included:

- `travel.js`

The revised Travel file keeps all old `Generation:` metadata working, while also supporting the new human-readable `Filter:` field generated by the admin page.

## Cloudflare Worker

`family-photo-worker.js` contains the existing public read routes needed by the website plus the password-protected write routes used by the admin page:

- `GET /folder`
- `GET /text`
- `GET /file`
- `GET /admin/ping`
- `POST /admin/mkdir`
- `PUT /admin/upload`

The original Worker source was not supplied, so this remains a complete compatible replacement rather than a literal edit of the deployed Worker. Back up the deployed Worker before replacing it. If the deployed Worker contains extra behavior, merge the `/admin/*` routes instead.

## Password

Create a Cloudflare Worker secret named:

```text
ADMIN_TOKEN
```

Its value is the family password entered on `admin.html`. It is **not** the Dropbox account password.

The browser keeps the accepted password only in `sessionStorage`, so closing the browser tab clears it.

## Dropbox permissions

The Dropbox app needs:

- `files.metadata.read`
- `files.content.read`
- `files.content.write`

`files.content.write` is the important new permission for uploads and folder creation. The admin code does not require `files.metadata.write`, file-request permissions, or sharing permissions.

After adding a new Dropbox scope, make sure the token/refresh-token authorization used by the Worker has been reauthorized with that scope.

## Dropbox structures created

### Recipe

```text
/Zohar Family/Recipes/Apple Cake.txt
/Zohar Family/Recipes/images/apple-cake-photo.jpg
```

There is no recipe item folder. The generated text contains the existing metadata and `[ingredients]`, `[preparation]`, and `[secrets]` sections expected by `recipes.js`.

### Trip

```text
/Zohar Family/Travel/Italy 1984/
    trip.txt
    images/
        photo1.jpg
        photo2.jpg
    itinerary.pdf
```

`trip.txt` contains Title, Year, Travelers, Filter, a backwards-compatible Generation value, Blurb, X, Y, and optional external links.

A user selects X/Y simply by clicking the map. They can zoom and scroll first, then drag the pin to refine it.

The Trip form can also automatically add the new shared trip to one or more personal Travel pages by updating:

```text
/Zohar Family/Works/{Person}/Travel/trips.txt
```

### Memories

```text
/Zohar Family/Memories/Cottage 2026/
    photo1.jpg
    video.mp4
    links.txt
```

`links.txt` uses the format already supported by the Memories page:

```text
Family video | https://example.com/video
Photo archive | https://example.com/photos
```

### Merch

```text
/Zohar Family/Merch/Family T-shirt/
    merch.txt
    front.jpg
    back.jpg
```

The folder name comes from the item name. `order:` is generated automatically; users never type it.

## Person's Page

The person's root remains:

```text
/Zohar Family/Works/{Person}/
```

### Works

```text
/Works/{Person}/Poems/...
```

Files and URL-only `.txt` links work with the existing Works archive.

### Personal Recipes

```text
/Works/{Person}/Recipes/Apple Cake.txt
/Works/{Person}/Recipes/images/...
```

The existing `recipes.html?person=...` page reads these directly.

### Personal Travel

The admin page loads the folders already present in `/Zohar Family/Travel` and lets the user check which trips should appear for that person. It updates:

```text
/Works/{Person}/Travel/trips.txt
```

The actual trip photos and documents remain stored only once in the shared Travel library.

### Personal Memories

The admin can upload media/links directly to:

```text
/Works/{Person}/Memories/{Album}/
```

It can also reference existing shared Memory folders/files through `albums.txt`, so the same photograph does not need to be duplicated.

### Personal Collection — Merch style

The existing family-site code recognizes a person's `Merch` folder as a special personal tab. `name.txt` changes the visible tab label, so the admin can make that tab say **Artifacts**, **Collections**, **Favorite Things**, etc., while still using the Merch card and quick-view design.

Example:

```text
/Works/Emily/Merch/name.txt          -> Artifacts
/Works/Emily/Merch/Grandpa's Camera/merch.txt
/Works/Emily/Merch/Grandpa's Camera/camera.jpg
```

The family-tree popup will display the tab as “Artifacts,” not “Merch.”

## Preview behavior

Previewing does not upload anything. Selected local photos/videos are rendered from temporary browser object URLs. Closing the preview releases those URLs.

The preview intentionally recreates the visual language of the relevant public page rather than loading an unpublished public URL, because the material does not exist in Dropbox yet. After publishing, the actual public page remains the source of truth.

## Cloudflare secrets

With Wrangler:

```bash
wrangler secret put ADMIN_TOKEN
```

Then use either the existing access-token setup:

```bash
wrangler secret put DROPBOX_ACCESS_TOKEN
```

or a refresh-token setup:

```bash
wrangler secret put DROPBOX_REFRESH_TOKEN
wrangler secret put DROPBOX_APP_KEY
wrangler secret put DROPBOX_APP_SECRET
```

Never put the admin password, Dropbox access token, refresh token, or Dropbox app secret in `admin.js` or `admin.html`.

## Large videos

Ordinary images, PDFs, and short videos can pass through the Worker normally. Very large videos may exceed Cloudflare request-size/runtime limits. If large archival videos become common, the upload route should be upgraded to a Dropbox upload-session flow.
